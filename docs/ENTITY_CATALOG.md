# Entity catalog and data quality

## Scope

`sv_dashboard` reads Home Assistant entities belonging to the Stellantis vehicle selected during config flow and creates its own package entities under the SV Dashboard config entry.

It does **not** recreate or rename upstream Stellantis entities. Visible entity IDs are generated by Home Assistant and can vary between installations; package mapping relies on device/entity metadata and technical translation keys rather than copied localized entity IDs.

SV Dashboard currently exposes package-owned `sensor`, `switch`, `button`, `number` and `time` platforms.

## Quality terminology

| Grade | Meaning |
| --- | --- |
| **Diagnostic** | Configuration/compatibility/status information. |
| **Direct / high** | Primarily direct upstream state or a valid odometer difference. |
| **Derived / medium** | Calculated value with useful source evidence but dependent on upstream timing/completeness. |
| **Estimated / low** | SOC/time/capacity-based approximation; not billing/certification data. |
| **Control** | Package-owned action or setting. |

## Package-owned sensors

| Sensor | Purpose | Data quality |
| --- | --- | --- |
| **Dashboard status** | Readiness, selected mapping, capability profile, modules and diagnostics. | Diagnostic. |
| **Server trip history** | Canonical Stellantis trip history for frontend/statistics use. | Raw source retained; invalid rows excluded from derived metrics. |
| **Server GPS history** | GeoJSON/history derived from available server positions. | Can be sparse; route lines are approximations. |
| **Server charge history** | Canonical/observed charging sessions and compact curve data. | Direct observations where available; reconstructed windows remain estimates. |
| **Vehicle information** | Brand, powertrain and available vehicle/maintenance information. | Runtime data can contain private vehicle identifiers. |
| **Trailing consumption (500 km)** | Rolling consumption over qualifying canonical trips. | Derived; electric energy can depend on SOC/capacity estimates. |
| **Distance since last charge** | Odometer minus reconciled last-charge baseline. | Direct/high when both values are valid; otherwise unavailable. |
| **Current trip energy** | Battery-side energy estimate for an observed trip. | Estimated/low. Electric-capability only. |
| **Last local trip result** | Restart-safe completed local trip result. | Distance may be high quality; electric energy/consumption remains estimated. |
| **Current charge power** | Battery-side charging-power estimate from SOC/time samples. | Estimated/low. Charging-capability only. |
| **Last local charge result** | Completed locally observed charging result. | Mixed direct/estimated fields. Charging-capability only. |

Not every vehicle receives every package-owned electric metric. Setup is capability-gated.

## Buttons

| Button | Action |
| --- | --- |
| **Wake vehicle now** | Calls the mapped upstream wake-up action and records diagnostics. |
| **Test notification** | Sends a test only when notification policy and recipients permit it. |
| **Sync server history** | Synchronizes canonical server history. |

A successful Home Assistant/upstream command call does not prove the physical vehicle performed the action.

## Switches

Available package switches can include:

- notification master;
- trip reports;
- charge reports for charging-capable vehicles;
- vehicle alerts;
- hourly wake-up;
- wake-up while charging where applicable;
- availability wake-up probe;
- one enable/disable switch for each explicitly selected Notify recipient.

Discovery never silently opts a Notify recipient in.

## Time settings

- quiet-hours start, default `22:00`;
- quiet-hours end, default `07:00`.

Quiet hours defer configured non-urgent availability warnings; they are not a global mute switch.

## Upstream entities

Depending on the selected vehicle, SV Dashboard can map upstream Stellantis entities for:

- mileage/odometer;
- tracker/current position;
- temperature;
- engine/driving state;
- electric SOC/range;
- charging state/type/end time/limit;
- fuel level/range/consumption;
- battery/SOH data;
- service battery;
- remote-connection/command status;
- supported upstream remote actions.

These are **not** package-owned entities. Their semantics, availability and refresh cadence belong to Stellantis Vehicles and the Stellantis service.

## Battery-capacity and residual rules

There is no generic fixed e-C3 capacity in SV Dashboard.

Capacity trust order:

1. current valid upstream capacity;
2. persisted last valid upstream capacity;
3. configured per-vehicle fallback;
4. unknown.

Residual-energy trust order:

1. current valid upstream residual;
2. SOC × trustworthy capacity where appropriate;
3. unknown.

Unknown values are omitted rather than fabricated.

## Canonical trip data quality

Canonical processing evaluates available distance, duration, speed and odometer continuity. Implausible rows remain retained for diagnostics but do not feed downstream metrics.

Where strong continuity evidence exists, only a **derived** boundary can be repaired; the raw upstream row remains unchanged and repair provenance is retained.

## Charging data quality

Observed charging sessions can retain timestamped SOC samples. Where direct charging energy/power is unavailable, battery-side estimates can be derived from SOC change, trustworthy capacity and elapsed time.

Such estimates:

- exclude charger/wallbox losses;
- depend on SOC granularity/update cadence;
- are not suitable for billing;
- are not raw BMS/wallbox telemetry.

Vehicles without charging capabilities do not receive these metrics/views.

## GPS data quality

Recorder tracker history can provide local position points where upstream actually updated. Canonical server history can add trip start/stop positions.

Current position stays separate from archived history. Straight server lines are approximate geometry, not a driven route trace.

## Long-term statistics

Statistics views may consume Home Assistant long-term statistics for supported mileage/SOH sources.

SV Dashboard does not conceal or directly rewrite malformed existing LTS history. The known mileage-statistics reset investigation is tracked in **issue #4**.

## Persistence

Package data is restart-safe and scoped per SV Dashboard config entry. Stores include local metrics/session state, canonical history and notification/wake-up state.

Removing/reloading SV Dashboard does not mutate the selected upstream Stellantis device or rewrite its Recorder history.

## Recorder retention

The default **History display window** is 2,160 hours (90 days). It is a query/display window, not Recorder retention policy.

SV Dashboard never changes Recorder retention, filters, database backend or purge schedule.

## Boundaries

SV Dashboard does not create household automations/scripts/`input_*` helpers and does not implement a direct Stellantis API client.

Package configuration uses the config/options flow and native `sv_dashboard` entity platforms.
